1. ESTRUCTURA DEL PROYECTO (relevado en esta sesion)
============================================================

Cheat interno (DLL de inyeccion) para Left 4 Dead 2, en C++,
compilado con MSVC/ClangCL como DynamicLibrary. Se inyecta en el
proceso del juego, espera a que "mss32.dll" este cargado
(DllMain.cpp) y luego hookea client.dll/engine.dll via MinHook.

Carpetas principales:
- src/SDK/         -> SDK reconstruido de Source Engine / L4D2
                      (interfaces, netvars, tipos de entidades)
- src/Utils/        -> Infra generica: HookManager (sobre MinHook),
                      SignatureManager (byte-pattern scanning),
                      BytePatchManager, InterfaceManager, Memory,
                      Singleton, Config (JSON/nlohmann)
- src/App/Features/ -> Features del cheat (Aimbot, ESP, Menu ImGui,
                      Misc, Movement)
- src/App/Hooks/    -> Hooks concretos (Copy_Command, CalcPlayerView,
                      EndScene, INetChannel_SendNetMsg, etc.)
- src/Storm/        -> Codigo/base "Storm" de referencia (mayormente
                      comentado / no activo)
- Release/          -> Build compilado (ByxStorm.dll)

Entry point: src/DllMain.cpp
  - DllMain crea un hilo (MainThread) que espera mss32.dll, llama
    App::Start(), y espera F11 para llamar App::Shutdown() y
    descargar la DLL.

Orden de inicializacion (App.cpp):
  SignatureManager::InitializeAllSignatures()
  -> BytePatchManager::InitializeAllBytePatches()
  -> InterfaceManager::InitializeAllInterfaces()
  -> HookManager::InitializeAllHooks()

Pipeline de hooks documentado (de BYX_STORM_PARTE2.txt, ya existia
antes de esta sesion, no generado por nosotros):
  Copy_Command (por tick): AutoDuck -> Bunnyhop -> AutoStrafe ->
    Triggerbot -> RapidFire -> Rage Aimbot -> Legit Aimbot ->
    MiscTools -> NoSpread -> CALL_ORIGINAL
  CalcPlayerView (por frame): CALL_ORIGINAL -> Thirdperson ->
    Silent Aim -> NoRecoil
  Paint: UpdateW2SMatrix -> ESP::Render -> MiscTools::Paint ->
    FOV Circle

2. REVISION: Bunnyhop.cpp
============================================================

Archivo: src/App/Features/Bunnyhop.cpp

VEREDICTO: Correcto. Es la tecnica estandar de "zero-delay bhop":
limpia IN_JUMP mientras el jugador esta en el aire
(!m_hGroundEntity().IsValid()), lo que evita que el motor detecte
"boton ya estaba apretado" (mv->m_nOldButtons & IN_JUMP) al aterrizar,
permitiendo salto automatico sin soltar la tecla.

Sugerencia menor (no aplicada): filtrar tambien por moveType
(noclip/observer) igual que se hace en AutoStrafe, para evitar
limpiar IN_JUMP innecesariamente en esos estados. Impacto: bajo,
inofensivo tal como esta.

3. REVISION: AutoStrafe.cpp - BUG CONFIRMADO
============================================================

Archivo: src/App/Features/AutoStrafe.cpp

La estructura general (calcular velDir y wishAng relativos al yaw,
rotar +-perfectDelta, reconvertir a forwardmove/sidemove) es correcta
y el round-trip de signos entre wishAng = atan2(-sidemove, forwardmove)
y sidemove = -sin(moveDir) es consistente.

BUG: el calculo de perfectDelta esta mal.

Codigo actual:
    const float maxSpeed = 1000.f;
    const float airAccel = 1000.f;
    const float wishSpeed = 1000.f;
    float term = (wishSpeed / airAccel) / maxSpeed * 400.f / speed;

Con los 3 valores iguales a 1000, la formula se reduce literalmente a
term = 0.4f / speed, sin importar los valores de las 3 constantes (se
cancelan entre si). Consecuencias:
  - term es casi siempre ~0 para cualquier velocidad razonable
    (>50 u/s) -> perfectDelta da practicamente siempre ~90 grados
    constante, sin importar la velocidad actual.
  - El bloque de clamp (term <= -1 || term >= 1) es codigo muerto:
    term nunca llega a esos extremos con esta formula.
  - Falta el frametime/tick interval (I::GlobalVars->interval_per_tick)
    por completo - la ganancia de aceleracion depende del tiempo
    entre ticks y no aparece en ningun lado.
  - "maxSpeed" no corresponde a nada en la formula real de
    CGameMovement::AirAccelerate - probablemente confundido con
    sv_maxspeed.
  - "airAccel" esta hardcodeado en 1000 en vez de leer el cvar real
    sv_airaccelerate (Source engine por defecto ronda 10-12; muchos
    servers de bhop/surf lo cambian).

FORMULA CORRECTA (derivada de CGameMovement::AirAccelerate,
consistente con lo que usan bots TAS/bhop conocidos, ej. hlstrafe):

    a = airAccel * wishSpeed * frametime * surfaceFriction
    cos(theta) = clamp((wishSpeed - a) / speed, -1, 1)
    theta = acos(cos(theta))

Fix propuesto (NO aplicado todavia al codigo):

    float tickInterval = I::GlobalVars->interval_per_tick;
    float airAccel = /* leer sv_airaccelerate real via ConVar */;
    float wishSpeed = 30.f; // cap hardcodeado del engine para air wishspeed

    float a = airAccel * wishSpeed * tickInterval /* * surfaceFriction */;
    float term = (wishSpeed - a) / speed;
    term = std::clamp(term, -1.f, 1.f);
    float perfectDelta = acosf(term);

Efecto esperado del fix: el angulo de giro pasa de ser ~90 grados
constante (ineficiente a baja velocidad, justo despues de saltar) a
una curva que arranca chico a baja velocidad y crece hacia ~90 grados
a medida que se acelera - ganancia de velocidad mas eficiente y
consistente, movimiento menos "robotico", y se adapta al
sv_airaccelerate real del server en vez de estar sintonizado a un
valor hardcodeado que no coincide con nada.

Pendiente de verificar empiricamente: la convencion de signo de
sidemove ("right" vs "left") - si el strafe curva para el lado
contrario al esperado, es un simple flip de signo, no un problema
estructural.

4.1 AIMBOT (Aimbot.cpp/.h, Aimbot_Rage, Aimbot_Legit,
    Aimbot_Common, Triggerbot, CBasePlayer_CalcPlayerView.cpp,

------------------------------------------------------------

[CRASH] #1 - Indice de hitbox sin validar
  Archivo: Aimbot_Common.cpp lineas 214-217 (Rage) y 285-291 (Legit)
  GetHitboxPosition() usa cfg.nBone (configurable por el usuario, sin
  clamp) o valores de kStormHitboxes contra pAnim->GetHitboxPos(nHitbox),
  que en studio.h:914 NO valida bounds. Si el indice excede
  numhitboxes real del modelo, lee un mstudiobbox_t basura y de ahi
  un ->bone basura que indexa BoneMatrix[128] - puede crashear el
  juego. La funcion muerta Aimbot.cpp::GetBonePos SI valida
  (bid<0||bid>=128), pero el camino que realmente se ejecuta no.

[FEATURE ROTA] #2 - Target Witch no funciona sin Target Commons
  Archivo: Aimbot_Common.cpp lineas 242 y 320
  Witches viven en el mismo rango de indices que los commons, que
  solo se escanea si cfg.bTarget_Commons esta activo. Si el usuario
  activa "Target Witch" pero no "Target Commons" (combinacion
  logica), el aimbot nunca adquiere Witch, en silencio.

[FEATURE ROTA] #3 - Silent aim override ignora bEnabled
  Archivo: CBasePlayer_CalcPlayerView.cpp linea 18
  bool bSilent = Rage::cfg.bSilent || Legit::cfg.bSilent;
  RageConfig por defecto tiene bEnabled=false, bSilent=true. El OR
  nunca chequea bEnabled. Si solo usas Legit con bSilent=false
  (querés ver la camara girar), Rage sigue "presente" con
  bSilent=true por default y este hook fuerza el angulo real cada
  frame, cancelando el aim visible de Legit.

[BUG LOGICO] #4 - Reuso de target sin chequear identidad de entidad
  Archivo: Aimbot_Common.cpp lineas 76-91, 180-183, 193/262, 210/282
  state.posHistory/velHistory/resolverData/lastTarget estan indexados
  solo por entindex(). IsEntityValid solo chequea pCE && !IsDormant(),
  nunca verifica que sea la MISMA entidad. Cuando un infectado muere
  y otro spawnea en el mismo slot (comun en L4D2), hereda historial
  de una criatura distinta -> picos de velocidad predicha falsos.

[BUG LOGICO] #5 - Fallback de switch-delay no revalida el target
  Archivo: Aimbot_Common.cpp lineas 246-248 (Rage), 324-326 (Legit)
  Si aparece un target mejor pero no paso flSwitchDelay, se descarta
  "best" y se sustituye por el target cacheado anterior SIN
  re-validar FOV/vision/salud ese frame. Si el target lockeado murio
  o quedo oculto el mismo tick, el bot sigue apuntando/disparando al
  anterior (a traves de pared o a un cadaver) hasta que expire el delay.

[DEAD CODE] #6 - Features::Aimbot::Run() nunca se llama
  Archivos: Aimbot.cpp, Aimbot.h
  Copy_Command.cpp solo llama a Rage::Run y Legit::Run. El Aimbot.cpp
  standalone (con sus propios globals bEnabled/bTargetLock/flFOV/etc)
  no se referencia en ningun otro lado - si algun panel de UI esta
  atado a esos globals, no hace nada. (Ademas tiene su propio bug de
  timer de target-lock que solo se actualiza al cambiar de target, no
  cada tick - moot mientras el archivo este inalcanzable).

[DISEÑO] #7 - Rage y Legit sin exclusion mutua
  Archivo: Copy_Command.cpp lineas 31-32
  Ambos corren sin condicion cada tick. Si los dos estan activados,
  Legit corre segundo y pisa el viewangle que puso Rage el mismo
  tick -> aim visiblemente peleando/tembloroso.

[FRAGIL] #8 - Offset crudo para lag-comp tick count
  Archivo: Aimbot_Common.cpp lineas 238 y 316
  float flSimTime = *(float*)((DWORD_PTR)pEnt+0x150);
  Existe NETVAR(m_flSimulationTime) dinamico en el SDK
  (c_baseentity.h:233) que se resuelve en runtime, pero este codigo
  usa un offset crudo 0x150 en su lugar. Si 0x150 no coincide con el
  offset real del build del juego (los netvars se mueven entre
  updates - por eso existe el sistema dinamico), flSimTime sale
  basura y tick_count se corrompe cada tick que hay target.

[MENOR] #9 - SmoothAngle siempre pone roll en 0
  Archivo: Aimbot_Common.cpp linea 156
  return Vec3(vCur.x+dx*t, vCur.y+dy*t, 0) - descarta el componente Z
  en vez de pasar vCur.z/vTgt.z. Impacto bajo (roll normalmente es 0
  en jugadores Source), pero es un descarte silencioso.

[MENOR] #10 - Mapas de historial nunca se podan
  Archivo: Aimbot_Common.cpp
  state.posHistory/velHistory/resolverData (std::map<int,...>) solo
  recortan cada VECTOR interno a 8/5/12 entradas, pero nunca borran
  la entrada del mapa externo cuando una entidad deja de aparecer
  (muere/se remueve). En sesiones largas con muchos commons
  spawneando, esto crece sin limite - memory leak lento, y es el
  mecanismo subyacente que habilita el bug #4.

No reportado como bug (verificado, se ve correcto):
  Math::VectorAngles/ClampAngles/NormalizeAngle y CalcAngle en
  Math.h manejan bien el wraparound de angulos via std::remainder;
  GetFOVToTarget/SmoothAngle en la Aimbot_Common.cpp viva normalizan
  bien el delta de angulo; null checks en pLocal/pCmd/pAnim/pTerror
  presentes y bien ubicados en los caminos vivos de Rage/Legit/
  Triggerbot; la formula "reversed delta" de CalcAngle en Math.h es
  matematicamente auto-consistente (verificado a mano con casos
  cardinales) aunque a primera vista parezca al reves.

[SILENCIOSO] #2 - HookManager traga cualquier fallo de MinHook
  Archivo: HookManager.cpp lineas 11, 18
  Los AssertFatal(MH_Initialize()...) y
  AssertFatal(MH_EnableHook(MH_ALL_HOOKS)...) estan COMENTADOS, y
  CHook::Create() (HookManager.h:15-18) nunca chequea el retorno de
  MH_CreateHook. Concretamente explotable: Copy_Command.cpp linea 15
  pasa Memory::FindSignature("client.dll", "...") directo como
  direccion destino del hook. Si esa firma alguna vez no matchea
  (parche del juego, build distinto), FindSignature devuelve 0,
  MH_CreateHook(nullptr, Func, &m_pOriginal) se llama y su fallo se
  descarta - el entry point de aimbot/bhop/strafe/triggerbot
  (Copy_Command) simplemente no se instala, sin error, sin mensaje, y
  el log de debug de la linea 19 de Copy_Command.cpp nunca dispara
  para dar la pista.

[CRASH] #3 - Use-after-free en shutdown: hooks se destruyen sin
sincronizar con el render thread
  Archivo: App.cpp lineas 40-43
  Shutdown() llama BytePatchManager->RestoreAllBytePatches() y
  despues HookManager->FreeAllHooks() (= MH_Uninitialize(),
  HookManager.h:47-50) ANTES de restaurar el WndProc, y el unico
  Sleep(250) ocurre DESPUES de ambos. FreeAllHooks() corre en el
  thread que detecto F11 (DllMain.cpp:20-24), totalmente
  independiente del render thread, que en ese momento exacto puede
  estar ejecutando dentro del trampoline de EndScene (que llama a
  ImGui, EndScene.cpp:29-38). MH_Uninitialize remueve y libera los
  trampolines de los hooks; si el instruction pointer del render
  thread esta en ese momento dentro de ese trampoline/detour ya
  liberado, falla. El Sleep(250) esta mal ubicado (despues del
  teardown, no antes) e insuficiente por si solo (ningun flag/mutex
  bloquea la entrada al hook del render thread) - presionar F11
  durante un frame activo es una ventana de crash real.

[CRASH DIFERIDO] #4 - Un scan de firma fallido no detiene la
ejecucion, entrega una direccion "resuelta" falsa
  Archivo: SignatureManager.cpp lineas 16-23; Assert.h linea 9
  AssertCustom solo hace pop de un MessageBoxA; no hace exit() ni
  return. Cuando Memory::FindSignature devuelve 0 (no encontrado),
  Initialize() muestra el messagebox y de todas formas ejecuta
  m_dwVal += m_nOffset, convirtiendo "no encontrado" en un entero
  pequeño cercano a null que CSignature::Get() entrega despues como
  si fuera una direccion valida. Cualquier consumidor (byte patches,
  direcciones de MAKE_HOOK, aritmetica de Client_Module + offset en
  Storm/Hooks/HookStormOthers.hpp) va a dereferenciar/saltar a traves
  de ese puntero falso, crasheando lejos de la causa real. (El
  MessageBoxA bloqueante en si mismo es tambien un problema: frena el
  thread de init esperando que un humano clickee OK dentro de un
  proceso de juego).

[CRASH SILENCIOSO] #5 - Config::Load/Save sin manejo de excepciones
  Archivo: Config.h linea 84 (input_file >> j;) y lineas 98-123
  (*static_cast<bool*>(var.m_ptr) = j[var.m_name]; etc.)
  Un archivo de config corrupto/mal formado tira
  nlohmann::json::parse_error; una config con un campo del tipo
  equivocado (ej. un string donde se espera un float) tira type_error
  durante la conversion implicita. App::Start() llama Config::Load(...)
  directo (App.cpp:32) sin ningun try/catch en toda la cadena, asi
  que cualquier default.json editado a mano o escrito parcialmente
  crashea todo el juego via excepcion C++ no manejada en vez de caer
  a valores por defecto.

[PARCHES NO SE RESTAURAN] #6 - BytePatchManager se bypassea por los
helpers reales de parcheo
  Archivo: BytePatchManager.cpp lineas 17-22
  InitializeAllBytePatches() esta completamente comentado. Mientras
  tanto Byte_Manager::Set_Bytes/Copy_Bytes y
  Redirection_Manager::Redirect_Function (BytePatchManager.h:24-90,
  duplicado en Memory.h:22-78 como Memory::Redirect_Function/
  Redirect_FunctionP) hacen VirtualProtect + sobreescriben bytes en
  client.dll/engine.dll directo (usado en HookStormOthers.hpp, ej.
  Redirected_Send_Move en la linea 1170) pero nunca registran nada en
  CBytePatchManager::originalBytes. RestoreAllBytePatches() (llamado
  desde App::Shutdown(), App.cpp:40) no tiene entonces nada que
  deshacer para ningun parche aplicado por este camino. Si ese codigo
  esta activo, el shutdown por F11 deja un stub "push addr; ret"
  permanente en el modulo destino, y MainThread descarga la DLL del
  cheat poco despues (DllMain.cpp:26,31) - cualquier llamada posterior
  a esa funcion redirigida salta a memoria ya liberada/desmapeada.

[SIN PROTECCION] #7 - Loop de dereferencia de InterfaceManager
chequea el puntero equivocado
  Archivo: InterfaceManager.cpp lineas 47-51
  if (Interface->m_pPtr) *Interface->m_pPtr =
  *reinterpret_cast<void**>(*Interface->m_pPtr);
  Interface->m_pPtr es &I::nombre, la direccion del puntero global -
  nunca es null. El chequeo deberia ser sobre *Interface->m_pPtr (la
  direccion recien resuelta) antes de dereferenciarla de nuevo.
  Combinado con el hallazgo #4 (un scan "exitoso" que entrega una
  direccion casi-null) o un offset que se pasa del limite de la
  imagen mapeada, esta dereferencia queda sin proteccion.

[UB] #8 - Retornos de VirtualProtect nunca se chequean
  Archivos: BytePatchManager.cpp lineas 6-7, 28-29;
  BytePatchManager.h lineas 26-90; Memory.h lineas 22-78
  Cada VirtualProtect(..., &originalProtection) ignora el BOOL de
  retorno. Si falla, originalProtection queda sin inicializar
  (comportamiento indefinido leerlo), y ese valor basura es el que se
  aplica despues como proteccion "de vuelta" - potencialmente dejando
  paginas del target con flags de proteccion equivocados (ej. codigo
  no-ejecutable, o RWX permanente) en vez de fallar ruidosamente.

[UNDERFLOW] #9 - Memory::FindSignature puede desbordar su limite de
scan
  Archivo: Memory.cpp linea 85
  for (auto i = 0ul; i < image_size - signature_size; ++i) con ambos
  operandos unsigned. Si signature_size > image_size (un patron mal
  configurado/sobredimensionado, o escanear un modulo inusualmente
  chico/parcialmente mapeado), la resta da underflow a un valor
  enorme y el loop lee muy fuera de la memoria del modulo, crasheando
  con access violation en vez de simplemente devolver "no encontrado".

[NO COMPILA EN DEBUG] #10 - Path de debug de FindSignature referencia
un identificador indefinido
  Archivo: Memory.cpp lineas 64, 106
  fmt::format("GetModuleInformation {} failed\n", sig) (y la segunda
  ocurrencia) referencian sig, pero el parametro de la funcion es
  szPattern - no hay ningun sig en scope. Como DEBUG_SIG solo esta
  definido bajo _DEBUG (Memory.cpp:55-56), esto significa que
  cualquier build en configuracion Debug de esta translation unit no
  compila.

[LATENTE, HOY INERTE] #11 - Race en Client_Module/Engine_Module en
DllMain
  Archivo: DllMain.cpp lineas 39-45
  CreateThread(..., MainThread, ...) se lanza ANTES de que
  Client_Module/Engine_Module se asignen, sin ninguna primitiva de
  sincronizacion entre las escrituras del thread cargador y las
  lecturas de MainThread. Hoy es inerte - cada hook/util de Storm
  recalcula su propio GetModuleHandleW(L"client.dll")/"engine.dll"
  localmente en vez de leer estos dos globals (confirmado: solo
  DllMain.cpp los lee, para logging) - pero es una mina para el
  futuro si algun codigo nuevo confia en que estos globals estan
  "listos" apenas arranca MainThread.

Nota adicional: Storm/Hooks/HooksStorm.cpp esta completamente
comentado salvo los includes - ninguna firma/hook de ese archivo esta
activa hoy; los hooks reales en produccion viven en App/Hooks/*.cpp.
